# Article Editing Guidelines

このリポジトリで記事を書く、または直すときの編集メモです。
textlint を通すだけでは拾えない、説明の流れ、引用、用語統一の確認に使います。

## 編集チェック

記事を直すときは、まず次を確認します。

- 見出し、表の前置き、まとめの導入に、説明用の定型句を置きすぎていないか。
- `ここでいう`、`これ`、`この軸` のような指示語が、直前の語や式を明確に受けているか。
- `豊かな`、`だいたい`、`ざっくり`、`よい` のような評価語やぼかし語を、具体的な名詞や条件に置き換えられないか。
- 式の直後では、`消す`、`近づける`、`大きくする` の対象を、変数名やモデル名で書いているか。
- 表だけ読んでも出典が見えるように、手法名のセルに脚注を置いているか。
- 略語、図、定訳が弱い手法名を、本文の流れの中で自然に説明しているか。
- 挨拶と記事の主題など、同じ導入の役割を持つ短い文を不自然に分けていないか。

チェック後に `npm run article-style:audit -- ./articles/<slug>.md` を実行します。
この監査は textlint では拾いにくい、過去に指摘された表現だけを機械的に見るためのものです。

## 基本方針

場当たり的な置換で直さないでください。読者がどこで引っかかったのかを先に見て、必要なら段落ごと組み替えます。
たとえば「略語の初出に正式名称がない」と指摘された場合、冒頭に略語一覧を足すのではなく、本文の自然な導入位置で正式名称、略語、引用を出します。

記事の最初に箇条書きが続くと読みづらくなりがちです。導入では、何を知っている読者に、なぜ今その話をするのかを段落で説明してください。
表は比較や記法整理には向いていますが、記事の動機や論旨の代わりにはしません。

## 指摘への対応手順

指摘を受けたら、すぐに置換しないでください。まず、指摘された文が段落の中で何をしているのかを確認します。

1. 指摘箇所の前後 1〜2 段落を読む。
2. その文の役割を、導入、接続、定義、根拠、図表説明、脱線、まとめのどれかに分ける。
3. 違和感の原因を、文体、接続、情報順、引用位置、用語、読者負荷のどれかに分ける。
4. 1 文の置換で直るか、段落の順序や役割を変えるべきかを決める。
5. 修正後に、前の文から自然に入り、次の文へ自然に進むかを読む。

特に導入、図表の前、外部リンクの前では、局所的に自然な文へ置き換えても、段落全体では浮くことがあります。
`図を置きます`、`この記事では`、`以下を紹介します` のような書き手側の説明は、読者に何を渡す文なのかを考えてから使います。

## 指摘を受けたときの抽象化

指摘を直すときは、まず原因を次の記事にも使える形へ分解します。
個別の文言や手法名をメモするだけでは足りません。同じ型の読みづらさが、別の語や別の章で再発するためです。

見る観点は次の通りです。

- 読者の負荷: 定義、略語、引用、図、表を一度に出しすぎていないか。必要な情報は、読者がその語を使う直前に置く。
- 対応関係: 引用、脚注、式、図の説明が、支えている語や主張の近くにあるか。文末にまとめると、何の根拠か分かりにくい。
- 移動後の整合性: 段落を移動して用語の初出位置が変わったら、正式名称、略語、引用も一緒に移す。後段に定義が残っていても、読者にとっての初出が裸の略語なら不備である。
- 説明の順序: 手法名を出した直後に、少なくとも「何を入力にして、何を省く、または何を最適化する手法か」を書く。読者が手法の輪郭を持つ前に、採用された理由や印象を書かない。
- 階層: 広い概念、狭い手法、具体例が同じ高さで並んでいないか。原則として、上位概念から具体手法、具体手法から事例へ下る。
- 見出し階層: 手法名が h2 で横並びになりすぎていないか。親見出しを作るのは、下に複数の小見出しがある場合に限る。小見出しが 1 つだけなら、`教師ありファインチューニング (SFT)` のように親子を統合する。
- 分類: 見出しの親子関係は、手法名の近さではなく教師信号で決める。同じ略語でも、区間選好を使う手法は選好系、自己蒸留を使う手法は蒸留系のように分ける。
- 因果: `広まった`、`注目された`、`出てきた` と書くなら、何が難しく、何を軽くしたのかまで書く。時系列だけでは説明にならない。
- 指示語: `これ`、`ここでいう`、`この軸` が、直前の何を受けているか。受け先が曖昧なら、名詞で言い直す。
- 図表前の接続: 図や表の直前で `この違い`、`この関係`、`この流れ` と書かない。図表が見る対象を、`教師信号の違い`、`更新軌跡の違い`、`データ形式の違い` のように名詞で書き、前段のどの論点から図表へ移るのかを明示する。
- 文体: 便利な定型句で段落をつないでいないか。接続詞で流れを作るのではなく、前の段落の問題が次の段落でどう処理されるかを書く。
- 動詞: `見る`、`整理する`、`まとめる` を万能動詞として使っていないか。比較する、切り分ける、評価するなど、実際の読み方や操作を書く。
- セクション間の接続: 導入や前段を組み替えたら、次の見出し直後の受け文も必ず見直す。年表や流れの説明をやめたあとに `ここまでの流れ` のような古い受け方を残さない。
- 役割の重複: 冒頭、図の前、`はじめに`、表の前で同じ宣言を繰り返さない。冒頭は動機、図の前は図を見る理由、`はじめに` は問題設定、表の前は表の読み方、のように段落ごとの仕事を分ける。
- 表後の本文: 表の直後に、表と同じ分類を文章でなぞり直していないか。表で済む対応関係は表に任せ、本文では例外、組み合わせ、次の章へ必要な差分だけを書く。
- まとめ表: `使い分け` や `全体像` の表と同じ内容を、まとめでもう一度表にしない。最後は表の再掲ではなく、筆者がどの判断を読者に残したいかを書く。
- 表の粒度: 後段で別系統として説明する手法を、全体像の表で 1 行に詰めない。教師信号やデータ形式が違うなら行を分ける。
- 用語: 直訳、造語、半角と全角の混在が、本文の理解よりも表記の違和感を目立たせていないか。読者が普段使う言い方を優先する。
- 列挙: 英字略語を複数並べるときに、`OPD、OPSD、SDPO` のような和文区切りと ASCII がぶつかっていないか。略語同士の列挙は `OPD / OPSD / SDPO` のように区切りを統一する。
- 目的関数: `目的を大きくする`、`距離を小さくする` だけで済ませず、期待報酬、損失、KL 距離など対象を名指しして、最大化するのか最小化するのかを書く。
- 役割: 文章、図、表が、動機、問題意識、背景、根拠のどれとして置かれているか。本文を書く理由でないものを `きっかけ` と呼ばない。図や表は `先に置く` のような執筆者側の都合ではなく、直前の論点と何がつながるのかを書く。
- 書き手の立場: 筆者の判断や温度が脚注にだけ出ていないか。本文が無人格な解説になっている場合は、脚注の材料を導入や段落の判断文へ戻す。
- 外部リンク: リンクだけを `参考になります` で置かない。直前の本文とリンク先のどの話題がつながるのかを 1 文で書き、本文ではどこまで扱うのかも必要なら限定する。
- 外部リンク: 複数のリンクで `次の記事が具体的です` のような同じ前置きを繰り返さない。リンク先が補う論点を、それぞれ別の名詞と動詞で書く。
- 複数リンク: bare URL を続けて置く場合は、各 URL が何を補うのかを直前の文で分ける。`前者` / `後者` だけでは、リンクを読む前に対応が分からない。
- 導入の密度: 挨拶、筆者の関心、問題設定、記事の射程、外部資料案内を 1 段落に詰めない。読者が最初に受け取る論点を 1 つに絞り、外部資料は別段落で役割を明示する。
- 導入の外部資料: `関連して` だけでスライドや記事を差し込まない。背景、前提、範囲外の補足など、本文に対する資料の役割を先に書く。
- 断片列挙: `A なのか、B なのか、C なのか` のように名詞句だけを並べると、違いの軸を読者に補わせる。導入では、`直接まねる`、`応答全体を評価する`、`途中の文脈へ細かく教える` のように、各項目が何をするのかまで動詞で書く。
- 教師信号の動詞: `教師信号を返す` は、誰が何を学習に使うのかがぼやけやすい。データや手法の説明では `教師信号にする`、`使う`、`与える`、`用意する` のように、学習側の動作が分かる動詞を選ぶ。
- 略語衝突: 同じ略語が別系統の手法名として出る場合は、表や見出しで分ける前にその衝突を説明する。後段の詳細説明まで待つと、表だけ読む読者には分類の理由が見えない。
- 章間接続: 前章の弱点を次章の冒頭でもう一度なぞらない。前章で述べた問題を名詞で受け、次章の方法が何を補うのかへ直接入る。
- 階層違いの併置: 論文やシステム名、学習構成、更新アルゴリズムを `A 型、または B 型` のように同じ高さで並べない。構成例、目的関数、更新手法のどれを指しているかを分けて書く。
- 評価テンプレ: 各手法を `長所は...弱点は...一方で...` の同じ型で説明し続けない。筆者が重く見る制約、使えるデータ、失敗条件から書き始め、評価語は必要な箇所にだけ置く。
- まとめの戻り先: 最後は手法名の再掲ではなく、冒頭で提示した問題へ戻す。AI エージェント、実装、データ選択などの動機を書いたなら、どの順番で判断するかまで具体化して締める。
- 執筆者都合の動詞: `置きます`、`置いておきます` は、図表やリンクを置く側の都合が前に出やすい。資料なら `載せます`、比較なら `分けます`、定義なら `定義します`、方法の位置づけなら `扱います` のように、読者が受け取る役割に合う動詞を選ぶ。
- 導入の無理な接続: 冒頭の動機に、後段の分析軸を無理に押し込まない。筆者の関心は自然な言葉で書き、教師信号や報酬などの整理軸は、その説明が必要になる段落で導入する。
- 範囲外宣言: `A には踏み込みません` のような範囲外宣言を導入で先に置きすぎない。読者が欲しいのは、まず何を扱うかであり、扱わないものは必要になった箇所で限定する。
- 範囲の動詞: `A に絞ります` は、書き手側の都合だけが見えやすい。導入やリンク前では `A を扱います`、`B はリンク先が詳しいです`、`C は別記事の主題です` のように、本文と外部資料の役割が分かる文にする。
- 曖昧なデータ名: `期待する入力`、`よいデータ` のような名詞句は、何を指すのかがぼやける。SFT の説明なら `入力と模範応答の組`、比較学習なら `勝ち応答と負け応答の組` のように、データ形式をそのまま書く。
- 背景の先取り: 背景では各節の詳細な弱点や式の読み方を先取りしない。後の節で説明する内容は背景から削り、背景には「なぜ次の分類が必要か」だけを残す。
- 導入部の再設計: 冒頭、背景、全体像のいずれかを直すときは、その 3 つをまとめて読む。指摘文だけを直すと、同じ分類宣言や列挙が別段落に残りやすい。

具体例は、原則を確認するためにだけ残します。新しい指摘を追記するときも、まず上のどの観点の問題だったかを書いてから、必要なら短い例を 1 つだけ添えます。

## 略語と正式名称

略語は、初出で正式名称を出します。形式は日本語名を先に置き、英語名と略語を半角カッコで添えます。

```markdown
教師ありファインチューニング (Supervised Fine-Tuning; SFT)[^instructgpt]
人間のフィードバックからの強化学習 (Reinforcement Learning from Human Feedback; RLHF)[^christiano]
直接選好最適化 (Direct Preference Optimization; DPO)[^dpo]
```

半角英数字の後ろでは半角カッコを使います。`Supervised Fine-Tuning（SFT）` のように、ASCII と全角カッコを混ぜないでください。
日本語名と英語名の対応も記事全体で揃えます。たとえば `大規模言語モデル (Large Language Model; LLM)` と書くなら、他の用語も `日本語名 (English; ABBR)` の形に寄せます。
導入で複数手法を順に説明すると、正式名称、略語、引用が多くなり、本文の流れが崩れやすくなります。導入ではできるだけ教師信号やデータ形式の話に留め、手法名の正式導入は各セクションに寄せます。
章や小見出しの冒頭で手法を改めて説明する場合は、前段に略語や引用が出ていても正式名称、略語、引用をそろえて再導入します。段落内の 2 回目以降だけ略語に戻します。

略語一覧を冒頭にまとめて置くのは、必要なときだけにします。本文の流れと関係なく定義が並ぶと、読者は覚える負荷だけを先に負います。

## 引用

重要な主張、手法の導入、歴史的な位置づけには引用を付けます。
引用は文末にまとめて置かず、対応する用語や主張の直後に置いてください。

```markdown
教師ありファインチューニング (Supervised Fine-Tuning; SFT)[^instructgpt] は、...
群相対方策最適化 (Group Relative Policy Optimization; GRPO)[^deepseekmath] は、DeepSeekMath[^deepseekmath] で導入され、DeepSeek-R1[^deepseek_r1] でも使われました。
Shen ら[^opd_geometry] は、OPD が SFT と RLVR の単なる中間ではないと述べています。
RLVR[^rlvr] / GRPO[^deepseekmath]
```

特に、用語そのものの出典を示す場合は、文末ではなく用語の直後に脚注を置きます。

```markdown
<!-- NG -->
知識蒸留では、教師モデルの出力分布を生徒モデルにまねさせます[^distillation]。

<!-- OK -->
知識蒸留[^distillation] では、教師モデルの出力分布を生徒モデルにまねさせます。
```

`広まりました`、`注目されました`、`出てきました` のような書き方は、それだけでは理由が分かりません。
何が重かったのか、何を避けたかったのか、どの論文や実装で見えるようになったのかを一緒に書きます。
`使われるようになりました` も同じです。採用の歴史を書きたい場合を除き、まずその手法が前の目的関数、データ、学習ループをどう変えるのかを書きます。

## 用語と表記

記事ごとに主用語を決め、本文全体で揃えます。
たとえば LLM の事後学習記事では、主用語を `事後学習` にし、初出だけ `事後学習 (post-training)` とします。
`後学習` のような別表記は混ぜません。

直訳っぽく不自然な日本語は避けます。
`単語片` のように読者が普段使わない言い方は、無理に日本語化せず `トークン` と書きます。
ただし `次トークン分布`、`トークンレベル信号` のように名詞を詰め込みすぎると読みにくくなります。必要に応じて `次に何を出しやすいか`、`細かい学習信号`、`出力の各位置` のように言い換えます。

英語のまま残す語と日本語へ寄せる語も決めておきます。
手法名として流通している `SFT`、`RLHF`、`DPO`、`GRPO` などは残してよいです。
定訳が弱い手法名は、無理に漢字の訳語を作らず、英語名と略語をそのまま使います。
一方で、説明文では `preference` を `選好`、`reward` を `報酬`、`reference model` を `基準モデル` のように寄せます。

## 段落の書き方

段落は、1 つの話題を導入し、その理由や具体例を置き、次の話題へ渡す単位として書きます。
短い文を並べるだけだと、メモの断片に見えます。逆に、1 段落に複数の論点を詰めると、読み手はどこを受け取ればよいか分からなくなります。

特に導入では、次の順で流れを作ると読みやすくなります。

1. 以前から使われている手法を置く。
2. その手法の実装上またはデータ上の重さを書く。
3. それを受けて次の手法がどの問題を軽くしたのかを書く。
4. さらに残る問題を示して、次の章へ渡す。

`も`、`さらに`、`最近は` は、直前の何に対する追加なのかが曖昧になりやすいです。
指す対象がはっきりしない場合は、接続詞を消すか、対比対象を明示してください。

## 見出し

見出しは、章のラベルとして読める形を優先します。
`RLHF と PPO: 報酬で応答を伸ばす` のような `手法名: ひとこと説明` は避けます。説明文を見出しへ押し込んだ印象になりやすいからです。
本文の冒頭で説明できるなら、見出しは `RLHF および PPO` のように簡潔にします。

ただし、見出しを短くした結果、章の入り口で何を読むのか分からなくなってはいけません。
見出し直後の段落で、その章が扱う問題、前章からのつながり、読む観点を補います。
表を置く場合も同じです。見出しの直後に表を出すのではなく、何を見るための表なのかを先に書きます。
表の前置きは長くしすぎません。表を読む観点が 1 文で伝わるなら、それで十分です。
`だいたい`、`ざっくり` のようなぼかし語は、意図して使う場合を除いて避けます。表の導入では、読む観点を短く断定します。
比較軸を 3 つ以上持つ内容には表が向いています。2 系統の違いや短い対比は、表にせず箇条書きや段落で並べる方が読みやすくなります。
親見出しで教師信号の分類を示す場合は、見出し末尾に手法略語を詰め込まない。手法名は本文冒頭や小見出しで出します。
Zenn 向けの記事では、通常の本文段落を途中改行せず 1 行で書きます。見出し、表、箇条書き、数式、URL 埋め込み、脚注定義はこの限りではありません。

## 技術記事で気をつける流れ

手法の並びは、年表ではなく「何に困って、何を変えたか」で説明します。
同じ階層ではない概念を並べるときは、広い概念から狭い手法へ、狭い手法から具体例へ進めます。
読者が先に上位概念を受け取り、その後に具体的な手法を位置づけられる順番にしてください。
たとえば `RLVR / GRPO` なら、RLVR を検証可能な報酬を使う広い枠組み、GRPO をその中の方策更新の 1 つとして扱います。

LLM の事後学習なら、SFT / RLHF / PPO / DPO / RLVR / GRPO / OPD / OPSD / SDPO の順に置くと、教師信号の違いとして読みやすくなります。

ただし、`DPO が最近出てきた` のような時間感覚は雑に書かないでください。
DPO は GRPO より前から使われています。一方、GRPO は DeepSeekMath で導入され、DeepSeek-R1 でより目立つようになりました。このくらいまで具体化します。
相対的な新しさを書く場合は、論文や公開日の引用を近くに置きます。

オンポリシーの話を出すと、読者はオフポリシーとの違いを知りたくなります。
OPD を説明するときは、固定データや教師生成データをまねる蒸留をオフポリシー側として短く置き、その対比で「現在のモデルが実際に生成した文脈上で学ぶ」と説明します。
GRPO から OPD へつなぐ場合は、疎な報酬と密な教師信号の対比を置くと読みやすくなります。

## 図の入れ方

論文の図を使う場合は、`images/<article-slug>/` 配下に記事名で分かるファイル名を付けて置きます。
本文では、図を置く前にその図を見る理由を 1 段落で書きます。キャプションには元論文名または著者名、図番号、脚注を入れます。
導入で図を先に出す場合は、図中の略語をそのまま本文初出にしないでください。本文やキャプションでは、正式導入前の略語を避け、`模範応答で学ぶ方法` のように内容で受けます。

## 式まわりの説明

`報酬モデルを消す`、`項を省く`、`分布を近づける` のような説明では、対象を具体的に書きます。
たとえば `明示的な報酬モデル $r_\phi(x, y)$ を学習せずに済ませる` のように、どの変数やモデルが不要になるのかを近くに置きます。
読者が直前の式と本文を対応づけられる粒度を保ってください。

## 最終確認

記事を出す前に、少なくとも次を確認します。

- 略語の初出に、日本語名、英語名、略語、引用が揃っている。
- 引用が、対応する用語や主張の近くにある。
- 半角英数字の後ろに全角カッコを使っていない。
- 主用語が記事全体で揃っている。
- 直訳調の用語を、読者が自然に読む表現へ直している。
- 箇条書きや表が、本文の論旨の代わりになっていない。
- `npx textlint ./articles/<slug>.md` を実行している。
